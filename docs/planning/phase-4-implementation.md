# gEdit: implementation plan for Phase 4

Scope: the roadmap's Phase 4, **"Comfort and geometry"** (`docs/planning/roadmap.md`): translate, rotate and mirror a program's path, expand drilling cycles into plain moves, report path lengths and an estimated run time, and give the editor the comfort features long-time users of NC editors expect (split view, printing, finding files in folders, typing help, named bookmarks, block ranges, inserting files, file associations, renumbering options, the side-by-side channel view, word-level compare marks, shortcut and colour settings, script packages, a form editor for profiles). Phase 4 is finished when the exit criteria in §2.2 pass.

Status: **plan of record since 2026-10-12, the owner's answers to §9 are in; P4a is on `main` (v1.1.0, draft built); P4e is built, reviewed and fixed (2026-10-17) and lands next**. The owner answered all 25 questions of §9 on 2026-10-12: 20 as proposed and 5 changed (Q4-2, Q4-9, Q4-14, Q4-23 and Q4-24), each marked under its question. The plan splits the work into eight milestones, in order of value; since 2026-10-17 P4e (the side-by-side channel view) comes right after P4a, then P4b, P4c, P4d and the rest (§9, "Channel view and order"):

| Milestone | What it delivers | Status |
|---|---|---|
| **P4a "Move the path"** | translate, rotate and mirror as bundled scripts on the Python modal interpreter, with a shared path tracker taken out of the extents script; on a lathe, translate and a Z mirror for the counter spindle; what cannot be judged is refused and listed, and a refused block means nothing is written | on `main` (`733f2e1`), released as v1.1.0 |
| **P4b "Drilling cycles and time"** | expand drilling cycles into rapid and feed moves; path lengths and an estimated time per tool; a machine's motion data (rapid rates, tool-change time, top feed) and limits (top spindle speed, travel) as a new, optional block of the machine configuration, also read by the program checks | planned |

Item 27 (the side-by-side channel view) is the reason split view comes first in P4e: its groundwork is a second editor and a model per pane, which split view builds.
- **What bug-fix round 1 and the TODO left in Phase 4 areas:** the `G76` second-block `P` (thread height) shown as written because the unit readers are not block-aware (TODO, "Two-block lathe cycles, what is left"); the Fanuc lathe `G83`–`G89`, the Okuma `G181`–`G189` and the Klartext pattern cycles without position roles (TODO, "Code-database gaps"); two instances of the app overwriting each other's state (TODO, "Data safety"), which file associations would make common; the extents' unresolved cycle depths and Okuma `L` radii (TODO, "M10 data gaps").
- **The owner's standing rules** (the memory notes, P2 §10, the handover): CAM output first and keep it simple; no backplot, no simulation, no DNC, no program management; machine-dependent readings are machine configurations with documented defaults; tapping speeds are left and reported, never scaled; the commercial reference editor is never named; manuals are sources of facts in our own words; an independent corpus of programs may be read for facts only, is never named or quoted, and evidence from it stays in `docs/planning/`; the owner's real programs stay local and are reported only as counts; a draft release follows each milestone that lands (D70; superseded on 2026-10-17, one release v1.2.0 with everything in TODO.md), and v1.0.0 stays unpublished (Q4-24); model and effort are chosen per task and shown per work package.
- **What the code says** (§1): the Python layer has modes and frames but no geometry model; the only position tracker and arc geometry are inside `extents.py`; the database has no flag that says "a drilling cycle with an R plane, a depth and a peck", no arc direction and no compensation side; the machine configuration has no rates or limits; the app has one code editor, no directory listing, no file associations and no print path. P4a and P4b therefore begin with data and a shared module, not with scripts.

## 1. Verified facts this plan relies on (at `f119784`)

- **F110. The Python modal state has no geometry.** `ModalInterpreter` (`src-tauri/resources/scripts/_nc_modal.py:487`, state at 1308–1332) tracks the plane (`sets.plane`, Klartext through `planeFromAxisWord`), absolute or incremental, the motion group as the last modal code, units, the feed unit (per minute, per revolution, per tooth, inverse time, travel time), the speed unit and clamp, diameter or radius (`diameter_reading`, 1448), open frames as a list of `{code, line, group}` without their values (1004–1069), tool centre point control and the rotary axes' state. The active cycle is `{code, line, pitchFeed}` only (937): **no cycle parameter is kept**. Sinumerik `TRANS`/`ATRANS` are a shift, not a frame; Klartext cycle 7 is an offset; Fanuc `G15`/`G16` are a frame (`polarCommand`); Sinumerik `AP=`, `RP=` and `G110`–`G112` are not in the database.
- **F111. The only position tracker and arc geometry live in `extents.py`.** `resolve_moves` (1043) resolves incremental moves from the last known position; `Extents.arc` (1110–1197), `centre_from_radius` (1522: a negative `R` is more than 180°, chord slack 0.002), `extremes` (1206) and `polar_move` (1230) do the geometry, from a vocabulary table at 93–121 (`G2`/`G3`, the profile's `arcCenter` and `arcCenterMode`, `R` and `CR`, Klartext `DR±`, `PR`/`PA`, `TURN=`, `AC()`/`IC()`). `CT`, `CTP` and `CIP` are always unresolved, and so are Okuma arcs with an `L` radius and `G102`/`G103`. The `R` plane of a drilling cycle is not computed and `G98`/`G99` are not read (they are a group without `sets`).
- **F112. Address arithmetic is the precedent for refusals.** `address_arithmetic.py` refuses a block per reason (`BLOCK_REASONS`, 245; `block_refusal`, 1380): an unknown code, a machine position (`G53`, `G28`, `M91`, `SUPA`), any open frame, a turned rotary axis without TCP, a call or modal macro with a chosen address, a cycle not reviewed or with a variable position, a cycle outside the XY plane, a pole it cannot move. It skips incremental words on add and subtract, variables, expressions, data words (`G92`, `G52`, `G10`) and FK points; it moves a cycle and the blocks that run it "in one piece, or not at all"; it reads every number on the machine and writes it back in its own form, rounding half away from zero only where the word's form forces it and reporting it ([user guide](../user/scripts.md#address-arithmetic)). A refused block is left and **the other blocks are changed**.
- **F113. The arc-centre convention is profile data.** `addresses.arcCenter` and `arcCenterMode: "incremental"` are in `fanuc-gcode.json`, `okuma-osp.json` and `sinumerik.json` (the lathe inherits); `AC()`/`IC()` override it per word; Klartext writes its centre as the pole `CC` (`pole: set`, used by `C`, `CR`, `CT`, `LP`, `CP`, `CTP`).
- **F114. The database has no arc direction and no compensation side.** `CodeSets` (`src/lib/core/codes/types.ts`) has `motion`, `path: 'arc' | 'cycle'` (read by the motion colours only), `radiusComp: 'on' | 'off'`, but nothing that says `G2` is clockwise or `G41` is left. Mirroring needs both, as data.
- **F115. There is no drilling-cycle flag.** Cycles are told by `group: 'cycle'`, `sets.cycle`, `modal`, `pitchFeed`/`tapping`, `blocks: 2`, `axisWords` and `CodeParam.position` (`'tool-axis' | 'none' | 'other' | 'mode'`, types.ts:77). Fanuc mill `G73`, `G74`, `G76`, `G81`–`G89`: `R` is tool-axis, `Q` a length, `P` a count, `K` a count. Fanuc lathe `G83`–`G89` and Okuma `G181`–`G189`: no position roles. Okuma `G80`–`G83` are contour (LAP) codes. Klartext `CYCL DEF 200`–`209`, `240`, `25x`, `262`: `Q203` tool-axis, the rest none; `CYCL CALL POS`/`PAT` positions `other`. Sinumerik `CYCLE81`–`89`, `CYCLE840`: `RTP`, `RFP`, `DP` (and `FDEP` of `CYCLE83`) tool-axis, `SDIS` and `DPR` none, `DTB` a dwell.
- **F116. A machine has no rates and no limits.** `MachineParams` (`src/lib/core/machines/types.ts:108`) has `numberInput`, `units`, `diameter`, `variants`, `modalInitial`; `channels` is stored in `MachineConfig.params` only and kept out of the effective key (P2 §7.16 #149). No rapid rate, top feed, tool-change time, top spindle speed, travel or acceleration exists anywhere; nothing converts a feed per revolution into a feed per minute or a surface speed into revolutions. Scale Feed's limits are form values. `MACHINES_VERSION` is 1 (Rust and TypeScript).
- **F117. The script contract.** Header fields `name`, `description`, `profiles`, `input`, `output`, `timeout`, `envelope`, `documents`, `params` (`src-tauri/src/scripts/meta.rs:57-67`); parameter types `number`, `integer`, `text`, `bool`, `choice`, `file`, `folder`, `address-list` (76–85); outputs `panel`, `replace`, `new-document` (one untitled document, `src/lib/app/scripts.ts:640-645`) and `report` (at most 5,000 rows and 1,000 findings). `documents` other than `active` is accepted with a warning and reset to `active` (`meta.rs:365-371`): **no script can read two documents today**. Every script is a command `script.run:<id>` without a key (`src/lib/contrib/scripts.ts:87`).
- **F118. One code editor.** `editorService.ts` drives one `IStandaloneCodeEditor` with one model per document; the compare diff editor is the only other widget, and its header records the two traps of any further instance (every editor option lands in the shared configuration service; a `theme` option sets the global theme; `src/lib/monaco/diff.ts:18-29`). No editor groups exist. View zones and scroll sync are public API (P2 F55); `setHiddenAreas` is not and fails over 300,000 lines (P2 F54).
- **F119. Keys.** `CommandDef.keys` is one key or `{mac, other}`; `findConflicts` (`src/lib/core/keys/keySpec.ts:340-357`) checks both platforms; `tests/unit/commandPins.test.ts` pins every shipped key against `tests/runtime/lib/shortcuts.js`. There is no user override file.
- **F120. Settings and texts.** Settings are one flat schema with `SETTINGS_VERSION` 1 (`src/lib/core/settings/schema.ts:26`); the dialog has five schema pages plus Machines and Profiles and no search. `t()` (`src/lib/i18n/index.ts`) has plurals through `Intl.PluralRules` and only English message files. The config folder is fixed (`src-tauri/src/paths.rs:407-416`); there is no zip support and no JSON Schema file for profiles or machines. M13 imports and exports single profile, code and machine files.
- **F121. Bookmarks** are line numbers without names, stored per file in `state.json` (at most 200 per file, 500 files; `src/lib/stores/fileMemory.ts`); there is no panel and no ribbon entry.
- **F122. Typing** reads `editing.forceUppercase` and `editing.preventLineJoin` only (`src/lib/contrib/typing.ts`); nothing handles Enter.
- **F123. Renumbering** implements `start`, `step`, `digits`, `max`, `onOverflow`, `spacesAfter`, `skipStartingWith`, `skipEmpty`, `restartAtProgramStart`, `onlyNumbered` and `altPrefixes`; `fitToMax`, `alignColumn`, `everyNth`, `skipContaining`, `skipFirst`/`skipLast`, `startTrigger` and `autoNumberOnEnter` are design-note names only. Reference rules (`src/lib/core/transforms/references.ts`): on Fanuc `M99 P` and `M98 P… Q…` are **reported**, `M98 Q` without `P` and `GOTO` are rewritten, `G70`–`G73 P/Q` are reported on the mill and rewritten on the lathe; Okuma `GOTO`, `IF` and `G85`–`G88 N…`; Sinumerik `GOTOF`/`GOTOB`/`GOTOC`. No rule for `G65`.
- **F124. The shell.** Tauri plugins: dialog, fs, window-state (`src-tauri/Cargo.toml:31-33`). No single-instance plugin (`src-tauri/src/recovery.rs:27-31` explains the heartbeat that replaces it), no `fileAssociations` in `tauri.conf.json`, `on_run_event` handles only `Exit` (`src-tauri/src/lib.rs:87-91`), no print path, and no command that lists a directory for the webview (`channels.rs` reads the metadata of named siblings only).
- **F125. Channels.** "Split into channel documents" makes untitled documents with a proposed name `<stem> <channel><ext>` (`src/lib/contrib/channels.ts:503-525`) and is a one-way copy; nothing shows two channels side by side.
- **F126. Compare** has review mode with six ignore options (`src/lib/core/compare/types.ts:76-81`); inside a changed line only Monaco's own character marks show.
- **F127. Tests.** A test that times work over 100,000 lines or more, or simulates typing, against a wall clock lives in `<name>.slow.test.ts` (`vitest.config.ts:8-36`, `CONTRIBUTING.md` "Tests"); the evidence gate exempts `docs/planning/` (`tests/unit/evidenceGate.test.ts`); no test checks the links of the Markdown documents.

### 2.2 Phase 4 exit criteria (testable)

Each criterion is proven by its milestone's tests and runtime scenarios on committed fixtures (synthetic, or the owner-public programs under `tests/fixtures/nc/owner-public/`); the owner's local programs are checked by G11 on their machine only, as counts. "Refused" always means: nothing in the document changes, and every reason is a row in Results with its line.

| # | Criterion | Proven by |
|---|---|---|
| X19 | **Translate.** On synthetic goldens for every built-in profile (`tests/fixtures/scripts/translate/<case>/`): a shift by dX, dY, dZ moves every absolute point, absolute arc centre (`AC()`, an absolute `arcCenterMode`), Klartext pole `CC`, cycle position and tool-axis cycle position (`R` under `G90`, `Q203`, `RTP`/`RFP`/`DP`), and leaves incremental words, incremental centres, radii and polar radii and angles as written; a lathe's dX is read as the machine reads `X` (diameter or radius, AD-43); each word is written back in its own form. A shift of 0, 0, 0 gives the program back **byte for byte** on every owner-public program it does not refuse; a shift by d and then by −d gives every word back its value. The extents of the result equal the extents of the original moved by the shift on every golden and every owner-public program it does not refuse (the differential oracle, §4 rule 7). | `test_translate.py`, `test_geometry_oracle.py`, `p4-geometry` |
| X20 | **Rotate.** In the XY plane of a milling profile, about a point by an angle: every point, arc centre vector and incremental move is rotated; `G2`/`G3` stay; `X` and `Y` are both written on every moved block (a block that wrote only one gets the other); Klartext `PA` turns by the angle, `IPA` stays; a rotation by 90°, 180° or 270° is exact; any other angle rounds each word to its resolution (AD-44) and every arc keeps its start and end radius within the tolerance of Q4-4, or the run is refused. Rotating by 360° gives the program back byte for byte; four rotations by 90° give every value back. | `test_rotate.py`, the oracle |

## 3. Architecture decisions

AD-19 (one modal interpreter, both languages), AD-31 (machine configurations, "no machine, no guess") and AD-32 (channels) of P2 §3, and AD-33–AD-40 of P3 §3 stay binding as written; the decisions below add to them.

**AD-41: The geometry transforms are scripts on one shared module, and a refusal means nothing is written.**
- Three bundled scripts, `translate.py`, `rotate.py`, `mirror.py` (the Tools tab's Built-in Scripts, each its own command), on a new helper module `_nc_geom.py`: the classification of every word of a block into a geometry role (absolute point, incremental point, arc centre absolute or incremental, radius, polar radius, polar angle absolute or incremental, pole, cycle position, tool-axis cycle position, data, untouched), the transform of a role, the write-back through `_nc_machine.py` in the word's own form, and the refusal reasons.
- **Refusal is all-or-nothing** (Q4-1, as the owner confirmed on 2026-10-12): address arithmetic changes the blocks it can judge and lists the rest (F112), which is right for a value change; for a path it is not — a contour moved except for one block is a broken contour. A geometry run that meets one refused block writes nothing and lists every refused block, so the user sees all of them at once.
- **Why scripts:** the roadmap's delivery column says Script; the work is a batch computation over the text on the Python interpreter, which is the oracle of the TypeScript one (AD-19), and users can read and adapt it (README principle 3). **Why not one script with an operation choice:** each transform has its own form (a shift, a centre and angle, an axis), and three commands are what a user looks for.
- **Why not a frame in the program** (inserting `G68`, `ROT`, cycle 10 or a datum shift instead of rewriting coordinates): that changes what the control does, needs the control's option, and leaves the path unreadable for the inspector and the checks; rewriting is what the design note asks for.

**AD-42: Mirroring swaps what the data says to swap.**
- New database flags, set by the P4a prelude and checked by G10: `CodeSets.arcDirection: 'cw' | 'ccw'` on the arc codes (`G2`/`G3` and their dialect forms) and `CodeSets.compSide: 'left' | 'right'` on the radius-compensation codes (`G41`/`G42`, Klartext `RL`/`RR` where they are entries); Klartext `DR+`/`DR-` read through a profile member that names the direction words of an arc (`addresses.arcDirectionWords`, the prelude's contract). `mirror.py` swaps a code for the code of the same group with the other value, so no code list lives in the script ("no consumer names a profile", P2 §8.8).
- A mirror also reverses the cutting direction: climb milling becomes conventional milling. The run says so in one warning; reversing the path to restore it is not offered (the design note keeps it for later, and it needs every block's order reversed).

**AD-43: Every number is read on the machine, and a lathe's X is a diameter when the machine says so.**
- The transforms read each word with `_nc_machine.py` (AD-31): a point-less word under "none" whose reading differs between the presets is refused, as in address arithmetic (D57).
- On a lathe, translate's dX is asked as the machine reads `X` (the form says "diameter" or "radius" and follows the document's machine; Sinumerik `DIAMON`/`DIAMOF`/`DIAM90` switches are followed per word, as `diameter_reading` does); `U` and `W` are incremental and stay.
- **The lathe Z mirror (Q4-2, decided 2026-10-12)** turns a main-spindle program into one for the counter spindle: Z mirrors about a Z the user gives (default Z0; `Z' = 2·Z0 − Z`), an incremental Z and `W` change sign, the arc centre vector along Z (`K`) changes sign, `X`, `U` and `I` stay (X is untouched, so no diameter reading is needed), and `G2`↔`G3` and `G41`↔`G42` swap **from the data of AD-42**, never from a code list. It works in the ZX plane (`G18`) only: this is the one lathe exception to the XY-only rule of Q4-3. **No rotation on a lathe**, and a mirror of X on a lathe is refused. Thread cycles, roughing cycles and Sinumerik turning cycles are refused in the first version (the prelude's case list decides the exact rule, P4a item 5). The result carries one warning that the tool nose direction (a number in the tool offset, not in the program) has to be set for the counter spindle.
- The distance mode at the first moved block comes from the program, or from the machine's power-on mode (`modalInitial`); a mode only assumed from the profile's default refuses the run (Q4-5). The design note's per-run options "arc-centre convention" and "distance mode to assume" are dropped: both are facts of the control (F113, the machine's power-on mode), and a run option would let a guess in (§7 records this).

**AD-44: Exact where it can be, rounded where it must be, and the arcs checked after rounding.**
- Translate, a mirror about an axis-parallel line through a decimal point, and a rotation by a multiple of 90° are computed exactly on decimal text (the `Decimal` rules of `_nc_machine.py`): no word is rounded.
- Any other rotation or mirror line computes in double precision and rounds each word half away from zero to its resolution: a point-less word to whole increments of the machine (IS-B 0.001 mm, an Okuma unit), a word with a point to the decimals the form asks (default: the word's own decimals, and at least three in mm, four in inch; Q4-4). Every rounded word is counted in the message.
- After rounding, every arc is checked: the distance from the centre to the start and to the end may differ by at most the tolerance of Q4-4, otherwise the run is refused at that arc (a control rejects or misreads such an arc). A radius arc keeps its radius; its chord is checked against it.
- Rotate writes `X` and `Y` on every moved block (a block that wrote only one now moves in both), from the position the path tracker knows; translate and the axis mirrors write only the words that were there. A block whose start position is unknown (no point written yet on an axis the transform needs) refuses the run.

**AD-45: Drilling cycles expand from a schema in the database, never from a code list.**
- A new member `CodeEntry.expand` (the P4b prelude's contract) says what a cycle does in steps the script knows: the approach (rapid to the position, rapid to the `R` plane or the set-up clearance above the surface), the feed in (in one, or in pecks with a retract to the `R` plane or by a distance), a dwell at the bottom, the way out (rapid, feed, feed with dwell, spindle stop and rapid), the return level (`G98`/`G99`, Klartext `Q204`, Sinumerik `RTP`), and which parameter is which (`CodeParam.expandRole`: position, r-plane, surface, depth, depth-relative, clearance, peck, dwell, return, feed, repeat). The expansion script reads only that.
- Only a cycle with a schema is expanded; the NC architect writes each schema from the manual, with a golden per cycle. Tapping cycles have no schema (a tap needs the spindle and the feed synchronized; plain moves break it, and tapping speeds are left as written by the owner's rule); nor do oriented boring (`G76`, the shift direction is a machine parameter), back boring (`G87`), manual-return boring (`G88`), the lathe cycles and Okuma's contour codes.
- **Machine-dependent steps are asked on each run** (Q4-9, decided 2026-10-12): the retract of a high-speed peck (`G73`) and the clearance of a deep peck (`G83`) are parameters of the control. The expansion form asks both **on each run**, prefilled from the machine's motion block (AD-46) when it sets them, and the field is required for a program that contains either cycle: without a value the two cycles cannot run, and the form says why. The motion mode after the cycle is the one the manual gives for the dialect, written on the next motion block when that block has no motion code of its own.
- The same expansion is used inside `statistics.py` (a module `_nc_cycles.py`), so the time estimate counts what the expansion would write. The statistics form asks the same two peck fields, prefilled the same way; it is a report, so it does not stop without them: a `G73` or `G83` without a value is counted as "not estimated" with its lines and the rest of the report is given (one rule for both scripts: the same fields and prefill, a refusal only where something would be written).

**AD-46: A machine's motion data and limits are an optional block of its configuration, outside the effective key.**
- `MachineConfig.params.motion` (rapid rate per axis in mm/min or in/min and the rotary rapid in degrees per minute, the rapid kind: `straight` (all axes on one line at the rapid rate) or `per-axis` (each axis at its own rate), the top cutting feed, the tool-change time in seconds, and the peck values of AD-45, which are only the prefill of the expand form) and `MachineConfig.params.limits` (top spindle speed per spindle, travel per axis in machine coordinates). Both optional, both additive: `MACHINES_VERSION` stays 1, as M12's `channels` did (D59).
- **Not in `EffectiveMachine.params` and not in `effectiveKey`** (the M12 pattern, P2 §7.16 #149): they do not change how a program is read, so changing a rate rebuilds no modal index. The script context gains `machine.motion` and `machine.limits` (additive, `contract` stays 2), absent when the machine has none.
- **Documented defaults:** none is a fact about any machine. A missing value is "not set" and the feature that needs it says so (the time columns, the peck prefill, the limit checks), instead of a number that looks like a machine's (Q4-10, Q4-11).

**AD-47: The time estimate is a lower bound and says so.**
- Time = length ÷ feed for every move, at 100 % override, with no acceleration, no block processing time and no look-ahead, so the machine is always slower; the report says this in one plain line. A feed per revolution is multiplied by the speed in force; under constant surface speed the speed follows the diameter along the move, held by the clamp in force or, without one, the machine's top speed (AD-46), and a move is split where the clamp starts to hold. Rapid moves use the machine's rapid kind and rates; the top cutting feed clamps a programmed feed above it. A dwell counts as written (the dwell class of `_nc_machine.py`). An inverse-time block takes 1 ÷ F minutes.
- What cannot be estimated is counted, never guessed: a multi-pass lathe cycle (`G71`–`G73`, `G76`), a thread or contour cycle, a pocket or pattern cycle, an Okuma LAP cycle, a feed per tooth (no tooth count is known), a subprogram call, a rotary move without a rotary rate.

**AD-48: The path tracker is taken out of `extents.py` before anything else uses it.**
- P4.1 moves the position tracker and the arc and polar geometry of `extents.py` (F111) into `_nc_path.py` without changing a result: every extents golden and every owner-public run stays byte for byte the same (the guard). The geometry scripts, the expansion and the statistics use the module; `extents.py` imports it.
- Why not a second tracker in `_nc_geom.py`: two trackers drift, and the TODO already lists duplicated script code as debt. Why not a TypeScript tracker: these are scripts (AD-41); the modal parity of AD-19 covers the modal state only, and the path tracker has no TypeScript reader.

**AD-49: Renumbering rewrites `M99 P` and `M98 P… Q…` inside the file, and lists what points in from outside.**
- A reference into another program of the **same file** (`M98 P1000 Q30` where `O1000` is in the file; `M99 P40` in a subprogram whose caller is in the file) is rewritten with the map of the program it points into, which the renumber builds per program (`restartAtProgramStart`). A target that is not in the file stays reported, as today.
- **Other documents:** after a renumber, references in the other **open** documents that point at a renumbered program of this file (`M98 P<this program>`, `CALL` and the like, from the profile's reference rules) are listed in Results; "Update the other documents" rewrites them, each document as its own undo step, after one confirmation; a file that is not open is never read or written (proposed, Q4-17).

**AD-50: Editor groups: one model per document, the focused pane is the editor; split view has two panes, the channel view one per channel (up to four).**
- `EditorService` gains groups: two for split view (side by side or stacked), and for the channel view of AD-51 one per channel, up to four (the owner, 2026-10-17: a three-channel program must show all three channels at once); each group is one `IStandaloneCodeEditor`, created with the shared instance options (`instanceOptions.ts`) and never a `theme` option (F118). The same document can be in both, sharing its model; each group keeps its own view state. `editorInstance()` answers the focused group's editor, so every command, decoration and panel follows the focus; the decoration owners (bookmarks, motion colours, compare marks, the inspector's highlight) register per editor.
- Why the cap of four: the owner's machines run up to three channels, and each pane adds the view-model cost of P2 F56; split view keeps two, because the header-while-editing case needs no more. The prelude measures the typing budget with four panes on a 300,000-line program (X29, X34). *Changed 2026-10-17 from "at most two": the plan had read the roadmap's channel view as two-channel only.*

**AD-51: A channel pane is a model of its own with a two-way mapping into the document.**
- **One file with channel sections:** each pane shows a model built from that channel's lines; an edit in a pane is applied to the document's model as the minimal edit of the mapped lines (one undo step of the document), and a change of the document (a transform, a reload, a machine switch) re-projects the panes. **One file per channel:** each pane is that channel's own document (its own dirty state and save).
- Alignment at the wait codes with view zones and locked scrolling are public API (P2 F55); no hidden areas are used, so a program over 300,000 lines works the same (P2 F54).
- Merging split channel documents back into their source uses the same mapping: the split records where each channel came from, and "Merge Channels Back" writes the channel documents' current text into those ranges as one undo step of the source, refused when the source changed in those ranges since the split.

**AD-52: Word marks come from the tokenizer of each side.**
- A changed line pair is tokenized with each side's profile; words are aligned by a small diff over the word sequence; a word that differs is marked whole, as a decoration on top of Monaco's own diff. In review mode the marks are computed on the normalized text and shown on it.

**AD-53: One read-only folder walk in Rust serves every folder feature.**
- A command `folder_search` (streaming, cancellable, a folder the user picked in the dialog, read only, no link followed out of it, a cap on files and on file size, binary files skipped and counted, the name pattern and dates checked before a file is read) serves Find in Folder; a narrower `folder_siblings` (one folder, names only) serves the channel sibling lookup. Both are reviewed under G8's security part (a new command that takes a path).
- Why not the fs plugin's directory scope: it would grant the webview a directory, which P2 §4 kept closed; a command that only answers what the search asked keeps the grant narrow.

**AD-54: File associations need one running instance.**
- The installer registers the extensions the owner confirms (Q4-21); macOS sends `RunEvent::Opened` to the running app, Windows and Linux start a second process with the path. A second process must hand its paths to the first and end, or the two overwrite each other's state (TODO, "Data safety"). The single-instance plugin of Tauri does this. P2 D42 deferred file associations for three reasons: the plugin had to be fetched over the network, several extensions are shared with other programs, and the installers could not be tested here. P4f answers them in turn: the dependency is added in the P4f prelude with the owner's OK and its licence checked by `licenses:check`; the extensions are the owner's list (Q4-21); the installers are a manual check (§10).

**AD-55: User keys are one file of overrides, checked like the defaults.**
- `<config>/keybindings.json`: command id → key (or `null` to remove a key), per platform where needed; read and validated like the other user files (bounded, JSON paths in problems); applied over the defaults at start and on save; `findConflicts` runs on the merged set for both platforms, and a conflict is shown on the Keyboard page and never silently resolved. A script's key binds `script.run:<id>`. The Keyboard page edits the file; the shortcut reference (View ▸ Keyboard Shortcuts) shows the keys in force.

**AD-56: A script package is a folder that adds user files, and switching it off removes them.**
- `<config>/packages/<name>/` with `scripts/`, `profiles/`, `codes/` (templates included), and a small `package.json` (name, version, description). Its files are read with the user files' rules (limits, validation, the M13 merge), as a layer between the built-ins and the user's own files; a setting `packages.disabled` lists the switched-off ones; a reload follows a switch without a restart. A package is as trusted as a user script: it is the user's folder.

**AD-57: The JSON Schemas drive the profile form and are held to the hand-written validators.**
- `schemas/profile.schema.json` and `schemas/machines.schema.json` are written by hand from the types (draft 2020-12), shipped and referenced with `$schema` in exported files; the form editor generates its sections and help from them. The hand-written validators stay the gate (P2 F6): a test holds both to the same answer on every built-in profile, every fixture profile and a set of broken ones, so a schema that drifts fails CI.

## 4. Execution protocol: deltas to P2 §5 and P3 §4

   - **Klartext `APPR`/`DEP` under rotate and mirror: allowed.** The first contour point of `APPR LT`, `LN`, `CT`, `LCT` and the end point of `DEP LCT` (and their `Z`) are points; `LEN`, the centre angle `CCA` (entered positive, at most 360°) and the radius `R` keep their values: the direction of the approach arc follows from the first (or last) contour element, and the sign of `R` says on which side of the compensation the tool comes in, so swapping `RL`↔`RR` from data keeps it right. This differs from the proposal ("`CCA` follows the rules of `C`"): `CCA` has no sign to follow. The polar forms (`APPR PLT`, `PLN`, `PCT`, `PLCT`, `DEP PLCT`) are not in the database and are refused like any form not covered. Source: HEIDENHAIN TNC 640 Klartext user's manual, approaching and departing the contour. (`CT`, `CTP` and `CIP` stay refused under rotate and mirror as X22 says; a later version can allow them under the exact operations, because their arcs follow from the transformed path.)
   - **Sinumerik `AR=`: stays under rotate and mirror.** The opening angle is unsigned (0 to 360°) and the direction is the code's, which the mirror swaps; the plan's proposal (a sign change under a mirror) would make a mirrored arc invalid. An arc by its centre and `AR=` with no end point leaves the position after it not known (§7 #294), so the next block that needs it refuses a rotate (`position-unknown`). The arc check does not apply to `AR=` arcs: the control computes the missing point, so no radius mismatch can arise. Source: SINUMERIK 840D sl programming manual, fundamentals, circular interpolation with opening angle.
   - **Fanuc helical arcs: the axes beyond the plane stay.** Up to two further axes move linearly with the arc; translate shifts their absolute values, rotate and mirror in XY leave them. A mirror turns a helix the other way, so a thread milled with it changes hand: the result carries the warning `helix-hand` (the Klartext manual's helix table shows the same: the hand follows from the turning direction and the direction along the tool axis). Sources: FANUC Series 30i/300i/300is Model A operator's manual, common to lathe and machining centre (helical interpolation); TNC 640 Klartext user's manual (helix).
   - **`G2`/`G3` with `R` under a mirror: the radius stays, sign included, and the direction swaps.** A negative radius means the arc over 180°, and a mirror keeps the angle an arc spans. The same holds for Sinumerik `CR=` (negative over 180°), Klartext `CR … R±` (the sign picks the larger or smaller arc, `DR` swaps) and Okuma `L` with `CALRG` (Okuma `L` arcs stay refused by X22; a later version can allow them under the exact operations). Sources: FANUC 30i operator's manual, common part (circular interpolation); SINUMERIK 840D sl programming manual; TNC 640 user's manual; Okuma OSP-P200L programming manual (direct radius command).
   - **The lathe Z mirror and threads: refused (`thread`).** Every block whose motion code or cycle has `pitchFeed` or `tapping`: `G32`/`G33`, `G76`, `G92` (system A), `G78` (system B), Okuma `G31`–`G37`, `G71`, `G72`, `G112`/`G113`, Sinumerik `G33`–`G35`, `G331`/`G332`; the Sinumerik thread cycles `CYCLE97`, `CYCLE98`, `CYCLE99` are refused as turning cycles. The hand of a thread follows from the direction of travel along Z together with the spindle's direction; the mirror reverses the travel, and whether the counter spindle's `M3` turns the same way seen from the part is a fact of the machine the program does not state. Sources: FANUC 30i lathe operator's manual (thread cutting, multiple threading cycle); Okuma OSP-P200L (thread cutting).
   - **The lathe Z mirror and `G71`–`G73`: refused in the first version (`roughing-cycle`).** A later version **can** allow a roughing cycle whose whole contour (`P` to `Q`) is inside the scope: the contour blocks mirror as points, the finishing allowance along Z (`W` of the second block of `G71` and `G72`) and the relief along Z of `G73` (`W` of its first block) change sign, and the depth of cut and the retract stay — the manual's four contour patterns give the signs of the allowances by the direction of the contour, which the mirror reverses in Z. The Okuma LAP (`G85`–`G88` with the shape codes) is refused the same way; its allowances are unsigned (the direction comes from the shape), so a later version would mirror the shape only. Sources: FANUC 30i lathe operator's manual (stock removal in turning, its patterns); Okuma OSP-P200L (LAP).
   - **The lathe Z mirror and Sinumerik `DIAMON`, `DIAMOF`, `DIAM90`: not refused.** The Z mirror leaves `X` and `I` as written, so how `X` is read does not matter to it. This differs from the proposal ("refused"). The Sinumerik turning cycles (`CYCLE92`–`CYCLE99`, `CYCLE930`, `CYCLE940`–`CYCLE952`) are refused (`lathe-cycle`): their parameters mix positions along Z with the side and direction of the machining. Source: SINUMERIK 840D sl programming manual (diameter programming); SINUMERIK cycles manual (turning cycles).
   - **The lathe Z mirror and the other cycles:** a single turning or facing pass (system A `G90`, `G94`; B `G77`, `G79`) without a taper is points and is mirrored; with its taper `R` it is refused (`single-pass-taper`), because the taper of `G90` is a difference in X (it would stay) and that of `G94` a difference in Z (it would change sign), which the data does not tell apart (FANUC 30i lathe manual, canned cycles). Every other cycle (`G70`, `G74`, `G75`, `G83`–`G89`, Okuma `G73`, `G74`, `G181`–`G189`, the Sinumerik drilling cycles) is refused (`lathe-cycle`). A C-axis word under the Z mirror is refused (`rotary-word`): seen from the counter spindle the C axis turns the other way.
   - **The tool-nose warning (`tool-nose`):** "Mirrored for the counter spindle: the tool nose direction (the cutting edge position in each tool's offset) is not in the program. Set it for the counter spindle before this program runs." Sources: FANUC 30i lathe manual (the direction of the imaginary tool nose is part of the offset); Okuma OSP-P200L (nose radius compensation through the T word).

**Goal:** a user sees two places of one program at once, edits the channels of a multi-channel program side by side lined up at their wait codes, sees in a comparison which words changed, and compares and merges two programs in an aligned side-by-side view.

**Status:** built, reviewed and fixed (2026-10-17); lands next. The prelude (contracts §6.7 and §6.11, stubs, pins, §7 #380–#392) was done on `p4e/base`, then Wave A (P4.21 editor groups and split view, P4.22a channel mapping, P4.24 word marks), Wave B (P4.22b channel panes, P4.23 merge back, P4.25 aligned diff with merge), P4.D (the user guide) and H4e (the scenarios `p4-split`, `p4-channels`, `p4-compare`, suite `p4e`, never run locally: GitHub only). The reviews found 14 NC and 13 code findings; the skeptic confirmed 18, held 8 partly and rejected 1 (NC-6, by design); the fix batches FA, FB1, FB2, FB3, FC, FE, FT and the follow-up FA2 fixed them (§7 #451–#472); the first runtime-suite run on GitHub found four more bugs and stale scenario numbers, fixed by GA, GB and GC (§7 #473–#479), with the owner's answers of 2026-10-17 (§9 "P4e review answers"). Left for later: the P4e backlog in TODO.md (CODE-4, CODE-5, NC-6, NC-8, the rest of CODE-11, a no-op redo after a refused edit once the view is closed, the jump-line re-read on 300,000-line programs, the runtime scenario as the only cover of the typing wiring in `AlignedDiff.svelte`).

**Prelude** (Opus, high — an exception to the rule of §4 rule 3 that the owner can veto: the editor-group contract is the base every editor feature then depends on, and the traps of F118 are where a second instance has gone wrong before; the owner agreed on 2026-10-12, Q4-25): AD-50's `EditorService` groups, the per-editor decoration registration, the commands (`view.splitEditor`, `view.splitEditorDown`, `view.closeSplit`, `view.focusNextPane`, `view.focusPreviousPane`, `channels.sideBySide`, `channels.mergeBack`), the test ids, the mapping contract of AD-51.

**Decided by the prelude** (2026-10-17; each with its reason; the owner's answers of the same day are in §9 and marked "owner" here):

1. **Undo with panes of one document is the document's history.** A pane of a program with channel sections has no history of its own that the user can reach: its edits are applied to the document as mapped edits that join the document's open undo element, and every boundary Monaco sets on the pane model (its `pushStackElement`, wrapped while the view is open) is set on the document too; the focus moving to another pane is one more boundary. Ctrl+Z, Ctrl+Shift+Z (Ctrl+Y on Windows and Linux) in a pane and Edit ▸ Undo/Redo run the document's undo; the pane where the change is takes the focus and shows it. *Why:* one program, one history (AD-51, X29); mirroring Monaco's own boundaries gives the same steps as typing in the program itself, without guessing where a word ends.
2. **One undo history with one file per channel (owner).** While the view is open a `ViewUndoStack` (§6.7 rule 15) orders the documents' own histories: an entry is a run of edits in one document between two boundaries, undo takes the newest entry back wherever it was made and focuses its pane. When the view closes the order is dropped and every document keeps its whole Monaco history; Save stays per file. *Why:* the owner asked for one history; storing only an order over the documents' own undo stacks keeps every document's dirty state, save and later undo exactly as they are without the view, and needs no text copies. *Limit, said in the user guide:* the order covers only edits made while the view is open (its history starts when the view opens, §7 #461). A file reloaded from disk is **one** entry of the view's history (`replaceAll` on the same model; Undo takes the reload back); only a document whose model was replaced drops its entries (§7 #469).
3. **Scrolling: always together (owner), no leading pane.** All panes share one vertical scroll position; the pane the wheel or the keyboard scrolled sets it for the others (horizontal scrolling stays per pane). *Why:* the filler zones make every aligned wait the same height in every pane and the trailing zones make the panes equally tall, so one scroll position is right for all of them; there is nothing to choose.
4. **The inspector, the program map and the status bar follow the active channel (owner).** The active pane is the one with the keyboard focus; `EditorService.cursor()` answers its cursor in **document** lines (the coordinate rule, §6.7 rule 3), so the inspector, the program map, the Channel and the cursor items of the status bar need no change. The active pane has a 2 px border in `--accent` (both themes; P4.21 holds it at ≥ 3:1 against the editor background, as the motion colours are held), the others a transparent one of the same width, so nothing moves when the focus does.
5. **Every pane has its own minimap and overview ruler (owner).** The minimap follows the setting "Show minimap" like the main editor; the overview ruler always shows the pane's wait marks (matched and unmatched), its bookmarks and its find results.
6. **Wait codes pair by the owner's rule (owner, 2026-10-17).** The same code with the same `P` set meets in exactly the channels the `P` names, the n-th occurrence in one with the n-th in each other (`waitKey`, `alignPanes`, §6.7 rule 12). A channel the `P` does not name gets nothing for it; a shown channel the `P` names that has no n-th occurrence (or has the code with another `P`) makes every shown mark of the occurrence unmatched; a named channel that is not shown is not judged. Two waits written in a different order in two channels: with two panes the longest run of occurrences that is in the same order in both is kept (a longest increasing subsequence, as Check Wait Codes' `out-of-order`) and the others are unmatched; with three or four panes the occurrence with the most crossings is dropped first, ties by pane and then line, capped (amended by review NC-5, §7 #457; the prelude's "the crossing occurrence of the lowest pane is dropped" gave poor results). The key above is the rule for every wait written with a `P` word, also for a rule built on the machine page; a wait whose partners are a list (`kind: 'line'`, the Sinumerik `WAITM`) pairs channel by channel instead, and a `SETM` answers it (review NC-4, §7 #456). *Why:* it is how the control reads the `P` word (paths as digits, the presets of the Fanuc lathe already say so); it generalises Go to the Matching Mark from two channels to N, and P4.23 moves `findPartner` onto the same key so both agree. Check Wait Codes keeps its own pairwise rule: for a rule with `samePartners` (the Fanuc presets) it reports the same situations as `partners-differ`, `missing` and `count-mismatch`.
7. **A pane's lines.** The header (the lines before the first section) is at the top of every pane, as Split into Channel Documents copies it; an edit in it shows in every pane. Lines after the header that belong to no channel are in no pane: the bar above the panes says how many, and Close Split shows them again. A document line no pane shows cannot be revealed in the view: the status bar says so and nothing moves. *Why:* the same projection as the split, so the merge and the view share one mapping; the header holds the program number every pane needs; inter-section lines are rare and editing them belongs to the program, not to a channel.
8. **More than four channels.** The view shows the first four channels in declared order and names the others in its bar; the Channel status item still reaches them. *Why:* AD-50 caps the panes at four; the owner's machines have at most three channels, so this is a rule for other machines, and a quick pick of four out of N would ask every time.
9. **Opening with one file per channel.** The channel documents that are open become the panes; when the sibling lookup (`channels.siblings`) finds a channel file on disk that is not open, the command opens the file dialog in the document's folder with multi-select, as "Open channel 2…" does, and goes on with what is open afterwards. Fewer than two open channel documents: refused in plain words. *Why:* standing rule 14 (P2 §4): the webview reads no file the user did not pick or drop, and the sibling lookup answers existence only.
10. **A selection across a junction.** In a channel pane, a selection whose lines are not one run of document lines (it spans the end of one section and the start of the next, over another channel's lines) is reported with `crossesJunction`, and the commands that act on the selected lines (transforms, the clean-up commands, scripts with a selection scope) refuse with "The selection runs over the lines of another channel. Select within one section." *Why:* acting on the document lines in between would change another channel the user cannot see in that pane; clamping would act on less than what is selected.
11. **Hover, folding and the outline in a pane.** The hover of a pane reads its modal context through the pane's mapping (P4.22b); folding and the breadcrumbs answer nothing in a pane in the first version (their providers find no document for a pane model). *Why:* a fold or a symbol computed on the program's line numbers would be at the wrong lines in a pane; mapping them is work no exit criterion asks for.
12. **Split view and the channel view exclude each other.** Split Editor is not offered while the channel view is open; Close Split closes either; a tab of another document in the channel view closes the view and shows that document. *Why:* four groups of two kinds at once would need a layout editor, which gEdit leaves out on purpose (no editor management beyond what the features need).
13. **Keys:** `F6` / `Shift+F6` move to the next and previous pane (free in gEdit and in Monaco 0.55.1; the F-key row is where gEdit's navigation keys are); no key for the split and channel commands (the usual split key needs AltGr on the owner's Swiss German keyboard; the `Mod+Alt` letters left are on the AltGr check). P4g's user keys can bind them.
14. **The typing budget (owner).** Split view (two groups on one 300,000-line document) and the channel view with two panes on a 300,000-line two-channel program keep the P1 budget, proved by `editorGroups.typing.slow.test.ts` (P4.21) and `channelPanes.typing.slow.test.ts` (P4.22b) on the pattern of `p3Typing.budget.slow.test.ts` (the code's work per keystroke: listeners, mapping, re-projection, alignment, motion colours per group), and by `p4-perf` (H4e) on the hosted runner for the WebKit part (each editor's view model, P2 F56). Three and four panes on 300,000 lines have no budget and no proof: such programs come from 3D and 5-axis milling, not from multi-channel lathes. The single-editor budget (`p3Typing.budget.slow.test.ts`) must not move.

### 6.1 The path tracker and the transform rules (`_nc_path.py`, `_nc_geom.py`; P4a)

Written by the P4a prelude; binding for P4.1–P4.5. The stubs carry the same text in their docstrings; where the two differ, this section wins and the stub is fixed.

**Where they sit.** Both are helper modules **above** `gedit_nc`: they import it and it never imports them, so the `_nc_*` internals `gedit_nc` re-exports stay as they are. A bundled script imports them by name (`import _nc_path`, `import _nc_geom`); the scripts README says they are internal (§7 #292). Standard library only, Python 3.9.

**The tracker (`_nc_path.py`, P4.1):**

1. **The line between the tracker and `extents.py`.** The tracker is everything of `Extents.line`/`Extents.block` that decides where the tool is: the interpreter update, a program start after the first (`called`, `unstated`), the written codes (`Extents.written`), the moves, the machine positions, the multi-pass cycles, the data blocks and the pole, a frame in force, unknown codes, the positions of a called cycle, `resolve_moves`, the polar move, the arc, what a cycle in force leaves unknown, and `report_units`/`units_switched` (which `value()` needs). `extents.py` keeps its ranges, scopes, work-offset and shift groups, the held rotary positions (`track_rotary`, `settle_held`; it reads `tracker.interp`), the diameter switches, the tool words, the machine rows (from `Step.moves` and `tracker.value`), the findings and every text.
2. **Events in the old order.** `Step.events` holds the `Unknown`s and `Reach`es in the order `Extents.block` raised and noted them: the resolve misses, the polar move (its miss or its extremes), the arc (its miss or its extremes), the block's end points, what the cycle in force leaves unknown; a data block's information row is an `Unknown` of kind `'data'` with no axes, raised only when the block moves something. `extents.py` replays them through `miss_axes` and `note` after its own work for the line (offsets, shifts, rotary state, tool words), which is the order it has today. That order is the guard of AD-48: every extents golden and every owner-public extents run stays byte for byte.
3. **Units and columns.** Positions are column values (a lathe's `X` a diameter where `PathAxes.lathe_column`), in `report_units`, fixed by the first **recorded** line that states `mm` or `inch`; a priming line (`record=False`) moves the path and fixes nothing. Arcs and polar moves are in coordinates (`PathAxes.geo`).
4. **The arc direction is data** (§6.2): `gedit_nc.arc_direction_of` of the motion code in force, or `PathAxes.direction_words` (`gedit_nc.arc_direction_words_of`) for a word written in the block, the address followed by its sign alone (`DR-1` in a tool call is no direction word). `ARC_CODES` and `DIRECTION_WORD` retire; the flags say what they said on the six databases (`geometryFlags.test.ts` pins `G2` → `cw`, `G3` → `ccw`), so no extents result moves. A code with `path: 'arc'` and no flag cuts no arc the tracker knows (`CIP`, `CT` are `UNRESOLVED_ARCS` as today; Okuma `G102`/`G103` stay end points only).
5. **Arcs in absolute coordinates, whatever the convention:** an incremental centre (`arcCenterMode: 'incremental'`, a centre word left out is 0), an absolute one (`'absolute'`, `I=AC(…)`), a radius (`R`, `CR=`; negative over 180°; `centre_from_radius`, chord slack `CHORD_SLACK`), the pole (Klartext `C`, `CP`), and `TURN=` above 0 as a full circle. `Arc.helix` names the axes that move with an arc outside its plane. Not resolved (an `Unknown` `'arc'`): `UNRESOLVED_ARCS`, Okuma `L` arcs, an arc by its end point and `AR=` with no centre, and — changed — an arc by its centre and `AR=` with no end point, whose end is **not known** (§7 #294). An **absolute** centre along a diameter axis (`I=AC(…)` under `DIAMON`, always under `DIAM90`) is read as that axis is, a diameter; an incremental one is a radius (`centre_reading`, §7 #302).
6. **Unknown, never guessed.** A position is `None` while not known and an `Unknown` says why, one id of `UNKNOWN_KINDS`; it stays unknown until a block writes the axis absolutely. `WordRead.unknown` carries the same id for one word.

**The transform rules (`_nc_geom.py`, P4.2):**


7. **Roles from data.** The profile, the database, the modal state and the tracker's `WordRead`s decide every role; the geometry vocabulary of `_nc_path` is the only list of names. A word nothing describes is `'unknown'`: under rotate and mirror it refuses its block (`word-unknown`: the Fanuc lathe's drawing-dimension `A`, Sinumerik `AP=`/`RP=`, whose pole `G110`–`G112` the database does not know); under translate a plain-letter one is left and listed (`word-left`) and an assignment word (`NAME=…`) refuses. An address the database declares for the codes of one group only (not of a motion or a cycle code) is that group's number where it is written without its code (Fanuc `D2`: the offset register; §7 #304).
8. **The operations.** `transform` works on geometric coordinates (a diameter word is halved by the caller and doubled by `write_word`); a translate's X shift is meant as `x_reading` says (the form follows the document's machine) and lands on each word in its own reading. Translate moves absolute points, absolute centres, the pole, cycle positions and tool-axis parameters, and leaves increments, incremental centres, radii and polar values. Rotate and mirror move points, centres, the pole and every incremental vector in XY; rotate adds the angle to `PA` and keeps `IPA`; mirror reflects `PA` (`2·degrees − PA`) and negates `IPA` (whole turns of the operation add nothing, the result stays in −360…+360; §7 #306); both keep radii (with their sign), `AR=`, `TURN=`, `CCA`, `LEN`, and the axes outside the plane. The lathe Z mirror negates `Z` about `z0`, an incremental Z, `W` and `K`, and keeps `X`, `U`, `I`, `R`, `CR=`, `AR=`. **Exact** (`is_exact`): translate, the lathe Z mirror, a rotation by a multiple of 90°, a mirror line parallel to an axis — decimal arithmetic, no rounding; a result that does not fit the word refuses (`resolution`). Otherwise: double precision, each word rounded half away from zero (its own decimals, at least `MIN_DECIMALS`; a point-less word to whole increments), every rounded word counted (`rounded`), and `check_arcs` on the **written** program (the tracker run over the result) refuses an arc whose radii differ by more than `ARC_TOLERANCE` (`arc-check`).
9. **Swaps from data** (AD-42): `swap_partner` finds the one entry of the code's group with the other value of the flag; none or two refuses (`swap-unknown`). The partner is written in the written style of the code it replaces (`G02` → `G03`, `G2` → `G3`). `swap_word` does the same with `addresses.arcDirectionWords`.
10. **Write-back** through `gedit_nc.write_back` in the word's own form: the address, a value function, a point or none, the leading-zero style, Klartext's `+` (the profile's `numberFormat.plusSign`, `'signed'` on Klartext: a signed word keeps a sign, so `Y-2.5` turned positive is `Y+12.5`; §7 #308) and decimal comma are kept; a word added by rotate (a block that wrote only `X` gets `Y`) takes the form of the other word of the plane in that block. With no machine chosen, a word whose result the presets would write differently refuses (`machine-dependent`), as in address arithmetic (D57); P4.2 may lift its helpers into `_nc_geom.py` (the TODO's duplicated-code item names the debt).
11. **The run** (the scripts, P4.3/P4.4): every block is judged before anything is written; a cycle and the blocks that run it, a definition and its calls, the pole and the moves around it are judged as one (a refusal of one member refuses all, address arithmetic's groups); `CYCL CALL POS X Y Z` (axis-named parameters, `position: 'other'`) are the cycle's position (`cycle-position` role) and move; any other `'other'` or unreviewed parameter refuses, and so does a call whose axis-named `'other'` parameters the block does not write (`CYCL CALL PAT`: its points are elsewhere) and a code that is nothing but `'other'` parameters (`PATTERN DEF`; §7 #301). **Resets** (§7 #299): a code that opens a frame refuses only where the modal state has a frame opened at its block, so its reset form (bare `ROT`, `CYCLE800()`, `PLANE SPATIAL SPA+0 SPB+0 SPC+0`, `CYCL DEF 10.1 ROT+0`, an empty `CYCL DEF 8.1`, `G69`) refuses nothing and leaves the blocks after it in no frame; a shift code with `shiftZeroIsNone` whose every axis value is zero (Klartext cycle 7, `G52`, `TRANS`, `ATRANS`) sets no shift; a value nobody describes in a shift block (`CYCL DEF 7.1 #5`) refuses. **Rotary axes** under rotate and mirror (§7 #300): a rotary word that leaves its axis at 0 refuses nothing; any other, and every move while a rotary axis stands away from 0, refuses (`rotary-word`). `axis-unwritten` concerns the axes a block moves incrementally (§7 #303). The Fanuc lathe's `G70`–`G76` and Sinumerik `CYCLE95` carry roles (§7 #305). Every refusal is a finding `{ line, severity: "error", message: "<as written>: <text>.", reason }`; information (`INFO`) and warnings (`WARNINGS`, the message being the text with a capital and a full stop) are findings too; a refused run hands the input back unchanged (Q4-1). The lathe Z mirror's cycle rules are the case list of §5 P4a item 5, all read from data (`pitchFeed`/`tapping` → `thread`; a `'start'` cycle with data axis words or a group holding a `contour` code → `roughing-cycle`; any other `sets.cycle` → `lathe-cycle`; a `path: 'cycle'` block with `R` → `single-pass-taper`).

### 6.2 Arc direction and compensation side (`CodeSets.arcDirection`, `CodeSets.compSide`; P4a)

1. **What a direction means.** `cw`/`ccw` as the **control** defines the code: seen from the positive end of the axis normal to the plane toward its negative end, in the right-handed system (G17 from +Z, G18 from +Y, G19 from +X). On a lathe in `G18` the same arc looks the other way round when the turret is behind the centre line; that changes how it looks on the machine, not what the code means, and the flag records the code's meaning. A mirror is the same swap whatever the viewing side. Sources: FANUC Series 30i/300i/300is Model A operator's manual, common to lathe and machining centre (circular interpolation); Okuma OSP-P200L programming manual (circular interpolation, the ZX plane seen from the positive end of the orthogonal axis); SINUMERIK 840D sl programming manual, fundamentals (G2/G3); HEIDENHAIN TNC 640 Klartext user's manual (`DR+` counter-clockwise, `DR-` clockwise).
2. **What a side means.** `left`/`right` of the programmed path, seen along the direction of travel, for cutter and nose radius compensation alike (Fanuc and Okuma lathes keep `G41`/`G42` for nose radius compensation). Sources: the same manuals, radius compensation.
3. **The swap rule.** A mirror writes, for a flagged code, the one entry of the **same group** with the **other value** of the same flag; if there is none or more than one, the block is refused (`swap-unknown`). A block of a selection that runs under a direction or a side set above the selection is refused too (`selection-mode`, §7 #309): the code to swap is outside the selection. `geometryFlags.test.ts` holds every shipped database to "exactly one partner"; that is why the five-axis Fanuc compensation codes and the C-axis contour arcs of Okuma are not flagged (§7 #297).

**Editor groups (P4.21)**

1. **One creation path, no theme.** Every group editor is created by one function of `editorService.ts`. The first editor of the window keeps `EDITOR_OPTIONS` (its `theme` is the fallback of a build without `contrib/theme.ts`); every other one, and any editor created while another exists, is built from `GROUP_EDITOR_OPTIONS`, which has no `theme` (F118: `create()` hands `theme` to the one standalone theme service). In the same synchronous block: the shared `updateOptions` payload is replayed (as today, G8 M2), then the group's **own overrides**. The overrides are a closed list — `readOnly` with `readOnlyMessage` (the group's document's lock), and for a channel pane `lineNumbers` (the document's line numbers, rule 14) and `wordWrap: 'off'` — applied with the instance's own `updateOptions` and never through `EditorService.updateOptions`. Because a standalone editor's `updateOptions` writes every option into the shared configuration service (`standaloneCodeEditor.js`, `updateOptions` → `updateConfigurationService`), the service re-applies every group's overrides after each shared `updateOptions` call, so the last writer never decides another group's look.
2. **The focused group is the editor.** The focused group is the last one whose editor had the text focus (`onDidFocusEditorText`), or the one `focusGroup`/`openGroups` named. `editorInstance()`, `cursor()`, `selectionLines()`, `selectedText()`, `insertText()`, `insertSnippet()`, `triggerAction()`, `presetFind()`, `focus()` and `onDidChangeCursor` act on it alone; `hasFocus()` is true when any group editor has the text focus. `docs.activeId` follows the focused group's document (a pane's document is its program); a tab click shows that document in the focused group, or focuses the group that already shows it; in the channel view a tab of another document closes the view first (decision 12). `onDidFocusGroup` fires on every change of the focused group, followed by a cursor event.
3. **The coordinate rule.** Every line number the service takes or answers is a **document** line. For a `pane` group the service maps through the pane's `PaneSource`: `cursor()` and `topLine()` answer the document line of the pane line, `selectionLines()` the document lines of the first and the last selected pane line, with `crossesJunction` when those pane lines are not one run of document lines; `reveal`, `selectLines`, `scrollToTop` and `insertSnippet`'s `at.line` take a document line and act in the group that shows it — the focused group first, then display order; for a program in the channel view, the pane whose channel holds the line. A line no group shows (outside every channel, decision 7) is not revealed: `reveal` does nothing and the caller's status message stands; `channels` and `contrib/navigation.ts` need no change. A caller outside `src/lib/monaco/**` never uses `editorInstance()` with a line number: P4.21 moves the three that do (`contrib/segments.ts` → `selectLines`; `app/session.ts`'s `topLineOf`/`scrollToLine` → `topLine`/`scrollToTop`) and hooks `contrib/typing.ts` to the focused editor on `onDidFocusGroup` and `onDidAttach`.
4. **The same document in two groups** shares its one model: an edit in one shows in the other, and there is one undo history (Monaco's own). Each group keeps a view state per document (cursor, scroll, folds), saved when the group shows another document or is detached, restored when it shows the document again. Model decorations (bookmarks, AD-50) show in both by themselves.
5. **Attach and detach.** `EditorHost.svelte` renders the layout: one `EditorGroup.svelte` per group, with a splitter between them (`side-by-side` and `channels`: columns of equal width, `stacked`: rows), each group's header (a document group: the document's title; a channel pane: the channel's name and, with one file per channel, the file's), and the channel view's bar above the panes (rule 14). `EditorGroup` calls `attachGroup` on mount and `detachGroup` on destroy; `detachGroup` saves the group's view state and disposes its editor, the group itself stays in the state; `attachGroup` builds a fresh editor by rule 1 and restores the state. The compare overlay unmounts every group and mounts them again on close (AD-6), so `captureEditorViewState`/`restoreEditorViewState` of `diff.ts` become redundant; P4.25 removes them with its entry. `ready` resolves on the first attach of `g1`; `onDidAttach` fires for every group editor that is built.
6. **The decoration owners register per editor.** Each owner paints every editor of `groupViews()` and listens to `onDidAttach` and `groups` for new ones:
   - **Bookmarks** stay model decorations of the document, so every `document` group shows them. A `pane` group gets a mirror: decorations on the pane model at `paneLine(line)` of every bookmark the pane shows, set again when the bookmarks or the projection change. Toggling in a pane toggles the document's bookmark at the cursor's document line (rule 3); the glyph margin stays a shared option.
   - **Motion colours**: one decorations collection per group editor, each painted from its own visible range; for a pane the visible pane lines are mapped to document lines and read with one `statesAfter` per run of consecutive document lines, at most `MAX_LINES` lines per group and update.
   - **Compare marks**: the diff editor is not a group (it replaces the group area, AD-6); the word marks of P4.24 are decorations of its two sides.
   - **The inspector** has no editor decoration: it follows `cursor()` and reveals through rule 3, and so do the program map and the status bar's cursor and Channel items (decision 4). AD-50's list named "the inspector's highlight" (§7 #380).
7. **Commands.** `triggerAction` runs in the focused editor; `undo` and `redo` from a channel pane go to `channelPanes.undo()`/`redo()` instead (rules 11, 15). Each editor has its own find widget.
8. **Closing and caps.** `closeGroup(id)` closes one group; one group left is `single`. `closeGroups()` returns to `single` with the focused group's document (for a pane: its program, at the cursor's document line). Split view has exactly two groups; the channel view two to `MAX_GROUPS` (4). A document closed while a group shows it: the group shows the document the store makes active, and split view with the same document twice becomes `single`; in the channel view a closed channel document closes its pane (fewer than two panes: `single`), a closed program closes the view.

**The channel view (P4.22a pure, P4.22b in the editor)**

9. **Opening** (`channels.sideBySide` on the active document; `channels.fresh`): no channels, a resolution that ran out of time (`channels.problems.tooSlow`) or fewer than two channels found → refused with a status message; more than four → the first four in declared order (decision 8). *Channel sections:* a pane per channel, its model `inmemory://pane/<docId>/<channelId>` in the document's language with LF, filled with `projectedLines(projectChannel(set, id))`, registered with `registerPane` (its `PaneSource` answers through `docLineOf`/`paneLineOf`), then `openGroups({ layout: 'channels', contents })`, the focus on the pane of the channel at the cursor. *One file per channel:* the open channel documents as `document` groups with `channelId`, in declared order; a channel file found on disk but not open is offered through the file dialog first (decision 9).
10. **Edits and re-projection** (`panes.ts` rules 1–6). A pane's content event that the module did not cause is mapped (`mapPaneEdits`) and applied to the document's model with one `pushEditOperations` call, without stack elements around it (they join the document's open element, rule 11). The document's content event (from a pane, a transform, a script, an undo, a reload) re-reads the sections (`channels.fresh`) and re-projects every pane with `reprojectEdits`, applied with the model's `applyEdits` (no history of its own) under a guard that keeps the module from mapping its own edits back. A channel that is no longer in the program leaves its pane open, empty and read-only, with a note in its header; a program that has no channels any more closes the view with a status message. A locked document makes every pane read-only. **A pane edit that would move lines to another channel is refused** (review NC-2, the owner, 2026-10-17): `paneEditMovesLines(before, after, edits)` compares the channel sets before and after the mapped edit; if it moves lines, the module takes the edit back inside the same undo element, re-projects the pane and says *A pane only edits its own channel's lines. To end a section early or add lines after its end, edit the program itself.* (`channelPanes.status.movesLines`). The refused edit is no entry of any history. A line typed or pasted just above a section start goes to the end of the section above, in the same channel (`mapPaneEdits`). §7 #455.
11. **Undo with channel sections** (decision 1). Every boundary Monaco sets on a pane model (its `pushStackElement`, wrapped for the time the view is open) is set on the document as well, and the focus moving to another pane is a boundary; so one step of the document is what one step in the pane would have been. Undo and redo of a pane are taken **at the model**: the pane model's `undo` and `redo` (and, with one file per channel, each channel document's) are replaced while the view is open, because every way to undo in Monaco (the keys, Edit ▸ Undo, the context menu) ends in `editor.getModel().undo()`; they run the document's undo or redo (§7 #467; the prelude's "key handler" would have missed the menu); after it, the pane whose lines changed takes the focus and its cursor goes to the first changed line.
12. **Alignment and scrolling** (`alignPanes`, `waitKey`; decision 6, the owner's rule). The marks come from `channels.fresh` — channel sections: the program's marks of each channel, mapped to pane lines; one file per channel: each document's own — and are lined up with filler view zones (`changeViewZones`, `heightInLines`, P2 F55), never hidden areas (P2 F54). The alignment is computed again after an edit that changes a pane's line count or a mark, and only the zones that differ are replaced. Word wrap is off in a pane, so a line is one line height and an alignment in lines is exact. **Scrolling is always together** (owner): every pane listens to its `onDidScrollChange`; a vertical change the module did not make itself is set on every other pane (`setScrollTop`); horizontal scrolling stays per pane. The trailing zones make the panes equally tall, so the panes reach their ends together.
13. **Marks.** A `matched` wait line carries `gedit-wait-matched`, an `unmatched` one `gedit-wait-unmatched`, both in the line-decorations margin and in the overview ruler; their hover says in plain words with which channels the wait meets ("Waits with Turret B, line 120") or which named channel has no matching wait ("Turret C has no matching wait for "M910P123""); an unmatched or unjudged mark says why from `Alignment.reasons` (`alone`, `missing`, `unknown`, `crossing`, `elsewhere`, `loop`, `answered`, §7 #458). A `none` mark gets no decoration. The colours are theme tokens of both themes, ≥ 3:1 against the editor background (held by a test, as the motion colours are).
14. **Per pane** (decisions 4, 5, 7). A pane's gutter shows the document's line numbers (`lineNumbers: (n) => String(docLine(n))`; with one file per channel the document's own); each pane has its own minimap (the setting "Show minimap") and overview ruler; the active pane's border is `--accent`. The bar above the panes (`channel-view-bar`) names the channels not shown and the number of lines in no channel.
15. **One undo history with one file per channel** (decision 2; `viewUndo.ts`). The module tracks every pane document, calls `noteEdit` on each content event it did not cause, `close()` on the focus moving to another pane and on every `pushStackElement` of a pane document's model (wrapped while the view is open), and routes the undo and redo keys and Edit ▸ Undo/Redo of a pane to the stack; an answer `refused: 'changedOutside'` is said in the status bar ("That file was changed outside the view. Close the channel view to undo in that file."); the stack starts when the view opens (`close()` on every tracked document at once, §7 #461). On close the stack is dropped; every document keeps its own Monaco history; Save, Save All and the dirty marks are per file as always.

**Merge back (P4.23)**

16. The rules are the header of `src/lib/core/channels/merge.ts`: Split into Channel Documents records `splitRecord(…)` (the header and every channel document's projection as made); `channels.mergeBack` is offered when the active document is a program with a record or one of its channel documents; `planMerge` refuses when the program changed in the lines (or the header) of a channel it merges (`channels.merge.sourceChanged`), when a channel document's header changed (`channels.merge.headerChanged`), and when the merged text would move lines between channels (`channels.merge.sectionsMoved`); it skips closed and unchanged documents; the caller writes the answer with `applyLines(source, 1, lineCount, lines)` as one undo step and renews the record. The record lives for the session (P4f decides whether written channel files keep it). `findPartner` (Go to the Matching Mark) moves onto `waitKey`, so it pairs exactly as the view lines up.

**Word marks (P4.24)**

17. The rules are the header of `src/lib/core/compare/wordDiff.ts`: words are the non-whitespace tokens of each side's tokenizer, aligned by a longest common subsequence, a changed word marked whole, an **address word** (letter and literal value, outside an expression) that only moved not marked (review NC-9: operands, variables, comments and calls are never cancelled as moved, §7 #452), no marks over `WORD_DIFF_MAX_WORDS` words a side; in review mode on the normalized text shown. In `diff.ts` the lines of one change pair in order up to the shorter side, the marks are a decoration of each diff side (`gedit-word-changed`), and Monaco's own character marks are not drawn while word marks show.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A transformed program runs into the part or the fixture | All-or-nothing refusal (AD-41); every assumption is a refusal reason (X22); the differential oracle and the fuzz review (§4 rule 7); exactness where possible and the arc check where not (AD-44); the owner's check on the machine's own simulation or a dry run (§10) |
| Rounding after a rotation makes an arc the control rejects | The arc check after rounding with the tolerance of Q4-4; the run is refused at that arc |
| A mirror turns climb into conventional milling unnoticed | One warning in every mirror result (AD-42) |
| An expanded cycle does something else than the cycle | Schemas only for the cycles the manuals describe step by step; extents equality per golden (X23); tapping and oriented boring never expanded; the peck retract and clearance asked on each run and required (AD-45) |
| The time estimate is read as a promise | A lower bound by design, said in the report; "not estimated" counted with lines; no built-in rate (AD-46, AD-47) |
| The extraction of the path tracker changes extents | Byte-for-byte extents goldens and the owner-public runs as the gate of P4.1 (AD-48) |
| A second editor breaks the main one (shared options, global theme) | AD-50: one creation path with the shared instance options and no `theme`; the code review names it; `p4-split` runs both themes |
| A channel pane's edit lands on the wrong lines of the document | A minimal mapped edit with tests on random edits against a full re-projection; a change of the source between split and merge refuses the merge (AD-51) |
| The folder walk exposes more of the disk than asked | A command that answers only the search, no directory grant, no link followed out, caps; the security review of G8 (AD-53) |
| Two instances overwrite each other's state once files open from the OS | The single-instance hand-over (AD-54) |
